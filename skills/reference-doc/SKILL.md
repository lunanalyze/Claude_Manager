# reference-doc

구현한 기능/패턴을 **코드 포함 참고 문서**로 정리해 허브(`Claude_Manager/docs/references/`)에 남긴다.
표준(strict rule)이 아니라 **참고(reference)** — "이런 요구를 이렇게 풀었다"는 재사용 가능한 사례집이다.

## 언제 쓰나
- 사용자가 "이 기능 어떻게 구현했는지 참고 문서로 정리/저장", "reference 문서 작성",
  "나중에 비슷한 기능 만들 때 참고할 자료로 남겨", "/reference-doc" 등을 요청할 때.

## 절차

### 1) 대상 확정
- **무엇을** 문서화할지(기능/패턴 이름), **어느 프로젝트·파일**인지 파악한다.
- 불명확하면 추측하지 말고 사용자에게 짧게 확인한다(대상 파일/디렉터리, 문서 제목).

### 2) 실제 코드 읽기 (위조 금지)
- 대상 코드를 **Read/Grep으로 실제로 읽는다.** 기억·추측으로 코드를 지어내지 않는다.
- 핵심 흐름을 이루는 파일들과, "비자명한 결정"이 담긴 지점을 찾는다.
- 문서화 대상 코드는 **다른 프로젝트**일 수 있다 — 코드는 그 프로젝트에서 읽고,
  **문서는 허브(`Claude_Manager/docs/references/`)에 저장**한다(단일 원본 원칙).

### 3) 문서 작성 (같은 폴더의 `TEMPLATE.md` 구조를 따른다)
원칙:
- **실제 코드 excerpt만.** 파일에서 그대로 옮기고, 어디서 왔는지 `파일경로:줄번호`로 인용한다.
- **전체 파일 덤프 금지.** 핵심·비자명한 조각만 발췌하고, 사이는 `// …` 로 생략한다.
- **"왜 이렇게 했는가"를 반드시 담는다** — 대안 대비 선택 이유, 트레이드오프, 함정.
  (미래 세션에 가장 값진 건 코드보다 "결정의 맥락"이다.)
- **검색 가능하게** 만든다: 명확한 제목, "언제 참고" 트리거 문장, 키워드/태그.
  참고 문서는 CLAUDE.md에 자동 주입되지 않으므로, 세션이 찾아오려면 제목·키워드가 중요하다.
- **참고 톤**: 강제 규칙이 아니라 "이렇게 풀 수 있다"는 사례. 프로젝트별 취사선택 여지를 남긴다.

### 4) 저장 위치·파일명
- 경로: `Claude_Manager/docs/references/<slug>.md`.
  분류가 늘면 도메인 하위 폴더(`references/<domain>/<slug>.md`)로 나눈다(README 관례 참조).
- `<slug>`: 영문 kebab-case, 내용을 드러내는 이름(예: `optimistic-ui-save`, `csv-streaming-export`).

### 5) 색인 갱신
- `Claude_Manager/docs/references/README.md` 의 "목록"에 **한 줄 포인터**를 추가한다:
  `- [제목](./<slug>.md) — 한 줄 훅(무슨 문제를 어떻게)`.
- 이미 있으면 중복 추가하지 말고 갱신한다.

### 6) 보고
- 저장한 문서 경로, 다룬 핵심 결정 1–2개, 출처(파일/커밋)를 사용자에게 요약해 전달한다.

## 품질 체크 (저장 전 자문)
- 이 문서만 읽고 **다른 프로젝트에서 같은 걸 재현**할 수 있는가?
- 코드 excerpt가 **실제 파일과 일치**하고 출처가 달려 있는가?
- "왜"가 빠지지 않았는가? (그냥 코드 나열이면 부족하다)
- 6개월 뒤 세션이 **키워드로 검색해 도달**할 수 있는 제목·태그인가?

## 설계 메모
- 이 skill의 단일 원본은 `Claude_Manager/skills/reference-doc/` 이며, 각 환경의
  `~/.claude/skills/` 에는 심링크로 설치한다(Claude_Manager/CLAUDE.md 원칙 2·3).
- 생성물(참고 문서)은 `docs/`(git 추적)에 들어가므로 WSL/Windows가 clone으로 공유한다.
