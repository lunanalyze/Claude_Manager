# remote-update

**별도 서버 없이** 도는 로컬 웹앱을 원격으로 갱신한다. 배포 서버를 두는 대신 **public GitHub
Release를 매 실행 시 조회**해서 새 버전을 알아낸다. 업데이트 파일도 그 release에 올린다.

이 스킬은 **특정 스택에 묶이지 않는다.** 아래 「계약」만 지키면 프런트가 무엇이든(React·Vue·
Svelte·바닐라), 백엔드가 무엇이든(Spring·FastAPI·Express·Go) 그대로 쓸 수 있다.
`assets/` 의 코드는 **참고 구현**이고, 계약을 지키는 다른 구현으로 갈아끼워도 된다.

---

## 두 가지 모드

| 모드 | 언제 | 하는 일 |
|---|---|---|
| **구축** | 프로젝트에 자동 업데이트가 아직 없을 때 | 배너 UI·업데이터·빌드 분리·`latest.json` 규격을 붙인다 |
| **릴리스** | 이미 붙어 있고 새 버전을 낼 때 | 버전 ↑ → 빌드 → 팩 → 검증 → 게시 → 게시 후 검증 |

요청이 "업데이트 기능 만들어"면 구축, "릴리스해줘"면 릴리스다. 애매하면 **물어본다.**

---

## 시작 전에 반드시 물어볼 것

### 1. 공개 저장소 (필수 — 추측 금지)

> "업데이트 파일을 올릴 **public GitHub repository**를 알려주세요 (`owner/name`)."

- **반드시 public이어야 한다.** 클라이언트가 인증 없이 `releases/latest/download/...` 를 읽는다.
  private면 설치된 앱이 401을 받고 업데이트를 영영 못 받는다.
- 코드 저장소와 **다른 repo여도 된다**(오히려 그게 흔하다 — 코드는 private, 배포만 public).
- 잘못된 repo에 올리면 되돌릴 수 없다. **사용자가 말한 repo만 쓴다.**

### 2. 그 repo가 public이라는 사실의 귀결

팩(zip)은 **누구나 내려받을 수 있다.** 그러므로:

- 팩에 **API 키·토큰·고객 자료·DB가 들어가면 안 된다.**
- 관리자 키를 심어야 하는 설치본은 **internal** 로만 만들고 공개 release에 올리지 않는다.

이 한 줄이 아래 「산출물 분리」의 존재 이유다.

## 계약 (이것만 지키면 스택 무관)

### C1. 앱은 자기 버전을 말할 수 있다

```
GET  <앱주소>/health        →  200  { "version": "1.4.2", ... }
```

경로 이름은 무엇이든 좋다(`/health`, `/api/health`, `/api/version`). **버전 문자열 하나**를
돌려주기만 하면 된다.

### C2. 버전의 단일 원본은 빌드 설정 파일이다

`package.json` · `build.gradle` · `pyproject.toml` · `Cargo.toml` 중 **그 프로젝트의 한 곳**이
원본이고, 빌드가 그 값을 실행 산출물에 심어 C1이 읽는다.

> 손으로 적지 말 것. 실행 중 버전과 `latest.json` 의 버전이 어긋나면 **알림이 영영 안 뜨거나
> 매번 뜬다.** 릴리스 스크립트는 빌드 설정에서 버전을 읽어 쓰고, 다르면 실패해야 한다.

### C3. 앱은 자신을 교체할 수 있다

업데이트 적용 요청을 받으면:

1. 업데이터를 **떼어낸 프로세스**로 띄우고
2. 자신을 **종료**한다 (자기 파일을 잡고 있으면 교체가 안 된다)

업데이터는 설치 폴더 **밖**(임시 폴더)에서 돌아야 한다. 자기가 교체할 폴더 안에서 돌면 갇힌다.

### C4. 교체 단위는 "앱 폴더" 하나다

```
<설치루트>/
  app/          ← 팩이 통째로 갈아끼우는 곳 (실행 파일·정적 자원·스크립트)
  runtime/      ← 런타임(JRE·Python 등). 업데이트가 건드리지 않는다
  data/         ← 사용자 데이터. 절대 건드리지 않는다
  <런처>
```

런타임을 `app/` 안에 두면 **업데이터가 자기 인터프리터를 교체하려다 죽는다.** 반드시 분리한다.

## 산출물 분리 — internal / external

```
<프로젝트>/build/installer/
  internal/     setup 설치본(.exe 등)  ← 사내 배포 전용. 공개 release 금지
  external/     업데이트 zip + latest.json  ← 공개 release에 올리는 것, 이 둘만
```

| | internal | external |
|---|---|---|
| 무엇 | 처음 설치용 전체 설치본 | 이미 깔린 앱을 갈아끼우는 팩 |
| 관리자 키 | 심어도 된다 | **절대 안 된다** |
| 런타임 포함 | 포함 | 미포함(`app/` 만) |
| 배포 | 사내 공유 폴더·USB 등 | GitHub Release |

`internal/` 에는 `README-사내배포전용.txt` 를 같이 만들어 **왜 공개하면 안 되는지**를 적어 둔다.
폴더를 나누는 이유가 바로 이 사고(설치본을 공개 release에 끌어다 놓음)를 막기 위해서다.

## 구축 모드 — 붙이는 순서

1. **공개 repo를 묻는다**(위 참조).
2. **계약 C1~C4 점검** — 없으면 만든다. 특히 런타임이 `app/` 밖에 있는지.
3. **업데이트 조회·적용 클라이언트** — `assets/update-client.js` 참고. 프레임워크 없는 순수
   fetch라 어디든 붙는다.
4. **배너 UI** — `assets/update-banner.html`(바닐라) 또는 `assets/UpdateBanner.tsx`(React).
   둘 다 같은 상태 기계다: `조회 → 배너 → 확인 → 적용 → 서버 복귀 대기 → 새로고침`.
5. **업데이터** — `assets/apply.py` 참고. Windows 파일 잠금 대응이 핵심이다
   ([windows-swap.md](references/windows-swap.md) 를 **반드시 읽고** 옮길 것).
6. **빌드 스크립트** — `assets/build-release.ps1` 참고. internal/external 을 나눠 만들고
   `latest.json` 까지 생성한다.
7. **첫 배포는 setup 설치본으로 한다** — 아래 「업데이터의 자기참조」 참조.

## 릴리스 모드 — 매 회차 순서

```
1. 버전 ↑        빌드 설정 파일 한 곳만 수정(C2)
2. 빌드          앱 빌드 → 팩 생성(internal + external)
3. 게시 전 검증   references/release-checklist.md 의 「게시 전」
4. 릴리스 노트    담당자가 읽을 문장으로 (커밋 메시지 아님)
5. 게시          external/ 의 **2개 파일만** 업로드
6. 게시 후 검증   같은 문서의 「게시 후」
```

각 단계의 구체 항목은 [release-checklist.md](references/release-checklist.md) 에 있다.

## 절대 하지 않는 것

### 게시된 에셋을 덮어쓰지 않는다 — 버전을 올린다

클라이언트는 **버전 문자열 비교**로 새 버전을 판단한다. 같은 버전 번호로 파일만 바꾸면,
그 버전을 이미 받은 사람은 **영영 갱신을 못 받는다.** 잘못 올렸으면 버전을 올려 다시 낸다.

### internal 설치본을 공개 release에 올리지 않는다

관리자 키가 들어 있다. 한 번 올라가면 내려도 이미 받아간 사람이 있다고 봐야 한다.
게시 전 검증에서 **에셋 개수와 이름**을 반드시 확인한다.

### 사용자 데이터·설정을 교체 대상에 넣지 않는다

`data/` 와 사용자가 등록한 키 파일은 교체에서 제외하고, 교체 중 잃지 않도록 **손에 들고
있다가 되돌려 놓는다**(`apply.py` 의 보존 목록).

## 업데이터의 자기참조 — 가장 비싼 함정

> **업데이터는 "지금 실행 중인 버전" 안에 들어 있다.**

그래서 업데이터 자체를 고쳐도 **한 번 성공적으로 올라간 다음 회차부터** 효력이 생긴다.
업데이터에 결함이 있어 업데이트가 실패하는 상황이면, 그 결함을 고친 버전도 **같은 결함 때문에
못 올라간다.**

빠져나오는 길은 둘뿐이다:

1. **setup 설치본을 한 번 배포**해서 고쳐진 업데이터를 심는다 (확실함)
2. 결함의 원인을 사용자 환경에서 제거해 옛 업데이터가 한 번만 성공하게 한다 (불확실함)

→ **최초 배포와 업데이터 교체 전환은 항상 setup 설치본으로 한다.** 릴리스 노트에도
"이 수정은 다음 업데이트부터 적용됩니다"를 적어야 사용자가 헷갈리지 않는다.

## 다른 스킬과의 경계

- **ship-guard** — 커밋·푸시 전 시크릿/대용량 스캔. remote-update는 **배포 산출물**을 다룬다.
  릴리스 전 코드 커밋이 필요하면 ship-guard를 먼저 부른다(중복 구현하지 말 것).
- **local-server** — 로컬에서 띄워 확인하는 일. 릴리스 검증에 서버 기동이 필요하면 그쪽을 쓴다.
