# Windows에서 앱 폴더를 교체하는 법

업데이트 실패의 대부분은 여기서 난다. **파일이 잠겨 있어서 폴더를 못 바꾼다.**
아래 표는 추측이 아니라 실측 결과다.

## 실측 — 무엇이 무엇을 막는가

`app\api\x.jar` 이 열려 있을 때:

| 시도 | 결과 |
|---|---|
| `app` 폴더째 rename | **WinError 5** (액세스 거부) |
| 자식 `api` 폴더 rename | **WinError 5** (열린 파일을 품은 폴더도 못 옮긴다) |
| 형제 `web` 폴더 rename | **성공** |
| 잠긴 파일 자신 rename | **WinError 32** (공유 위반) |

다른 프로세스의 **작업 디렉터리(CWD)만** `app` 안일 때:

| 시도 | 결과 |
|---|---|
| `app` 폴더째 rename | **WinError 32** |
| `app` 의 자식 항목 이동 | **성공** |

### 여기서 나오는 세 가지 사실

1. **WinError 5 는 "권한 문제"가 아니다.** `app` 안의 어떤 파일이 열려 있다는 신호다.
   (권한이 의심되면 같은 폴더에 임시 폴더를 만들어 rename 해 보면 1초에 판별된다.)
2. **폴더째 rename 은 가장 약한 방법이다.** 안에 열린 파일이 하나만 있어도 통째로 막힌다.
3. **자식 항목 이동은 폴더 핸들과 무관하다.** 교체는 이쪽으로 해야 한다.

## 교체 전략 — 세 겹

### ① 교체 전에 잠금이 풀렸는지 확인한다

**포트가 닫힌 것은 프로세스가 끝난 증거가 아니다.** 웹서버는 커넥터를 먼저 닫고 프로세스는
잠깐 더 살아 실행 파일을 쥐고 있다. 다른 인스턴스가 떠 있으면 아예 놓지 않는다.

파일을 수정하지 않고 검사하는 법 — `CreateFileW` 를 **공유 금지(dwShareMode=0)** 로 열어 본다.
다른 핸들이 있으면 `ERROR_SHARING_VIOLATION(32)` 이 난다. 열리면 즉시 닫으므로 파일은 그대로다.

```python
h = kernel32.CreateFileW(path, 0x80000000, 0, None, 3, 0x80, None)  # GENERIC_READ, share=0
busy = (h == INVALID_HANDLE_VALUE and ctypes.get_last_error() == 32)
if not busy: kernel32.CloseHandle(h)
```

앱 폴더 전체를 훑어 **열린 파일이 없어질 때까지 기다린다**(상한 2~3분). 끝까지 안 풀리면
**아무것도 건드리지 않은 채** 중단하고, 어떤 파일이 잡혀 있는지·설치 폴더에서 어떤 프로세스가
돌고 있는지 로그에 남긴다. 다음에 원인을 추측하지 않아도 된다.

### ② 폴더째 rename 하지 말고 내용만 옮긴다

```
app/        ← 이 디렉터리 자체는 절대 rename 하지 않는다
  api/  web/  ...  ← 이 자식들만 app.bak/ 으로 옮긴다
```

`app` 을 잡고 있는 핸들(탐색기 창·백신 폴더 감시·검색 인덱서)이 있어도 자식 이동은 통과한다.
실패해도 실패 지점이 "폴더 전체"가 아니라 "그 항목 하나"로 좁혀져 안내할 수 있다.

### ③ 막힌 폴더는 한 겹 들어간다 (재귀 폴백)

자식 폴더가 막히면 그 폴더의 **내용만** 옮기고 껍데기는 그 자리에 둔다. 새 팩은 어차피 그
경로에 파일을 쓰므로(폴더가 이미 있어도 무해) 교체가 완성된다.

되돌리기 경로에서 "대상 폴더가 이미 있음"(WinError 183)이 나오는 것도 같은 이유다 — 같은
방식으로 **병합**하면 된다.

> 잠긴 것이 **파일**이면 어떤 방법으로도 교체할 수 없다. 그때는 이름을 알려주고 설치를
> 원래대로 둔 채 실패한다. 요행을 바라고 덮어쓰려 하지 말 것.

## 롤백

```
1. app/ 의 내용 → app.bak/ 으로 이동
2. 팩 전개 → app/
3. 보존 파일 되돌려 놓기(키 파일 등)
4. 앱 기동 → 헬스체크
   ├ 통과 → app.bak/ 삭제. 끝
   └ 실패 → app/ 비우고 app.bak/ 내용을 되돌린 뒤 다시 기동
```

2~3 중 어디서 실패해도 **1을 되돌릴 수 있어야** 한다. 반쪽짜리 `app/` 로 앱을 띄우는 것이
업데이트 실패보다 나쁘다.

## 콘솔 창이 쌓이는 문제

`start "" foo.cmd` 는 Windows가 **`cmd /K foo.cmd`** 로 띄운다. 스크립트가 `exit /b` 로
끝나도 **cmd 자체는 살아남아 창이 그대로 남는다.** 업데이트 한 번에 죽은 콘솔이 하나씩 쌓인다.

실측:

| 실행 | 스크립트 끝 | 결과 |
|---|---|---|
| `start "" s.cmd` | `exit /b 0` | 창 **남음** |
| `start "" s.cmd` | `exit 0` | 종료 |
| `start "" cmd /c s.cmd` | `exit /b 0` | 종료 |

→ 런처·업데이터 스크립트는 **`exit`(not `exit /b`)** 로 끝낸다.
단 **실패했을 때는 `pause` 로 붙잡는다** — 오류가 안 보이고 창이 닫히는 게 더 나쁘다.

업데이터는 교체 **전에** 이 설치본의 남은 런처 콘솔을 정리한다(그 시점엔 앱이 이미 끝나
아무 일도 하지 않는 껍데기다). 재시작 직전에만 정리하면 **이미 늦다** — 남은 콘솔이 앱 폴더
안의 스크립트를 읽고 있으면 그 핸들이 교체를 막는다.

## 브라우저 탭이 두 개가 되는 문제

업데이트를 시작한 탭은 이미 서버 복귀를 기다렸다가 **스스로 새로고침**한다. 그런데 재시작한
런처가 브라우저를 또 열면 같은 주소의 탭이 두 개가 된다.

→ 업데이터가 앱을 재시작할 때는 **브라우저를 열지 않는다.** 런처에 `--no-browser` 같은 인자를
주거나, 런처가 읽고 스스로 물러나는 **일회용 표식 파일**을 남긴다.

> 런처가 설치 루트에 있어 팩(`app/` 만 담는다)으로 갱신되지 않는 구조라면, 표식 파일 방식이
> 유일한 방법이다 — 팩으로 갱신되는 쪽(`app/` 안의 스크립트)이 표식을 보고 판단한다.
> 표식은 **본 즉시 지운다.** 남아 있으면 다음 정상 실행의 브라우저를 한 번 삼킨다.

## 업데이터가 자기 인터프리터를 밟지 않게

업데이터는 **설치 폴더 밖**(임시 폴더)에서 돌고, 쓰는 런타임은 `app/` **밖**에 있어야 한다.
`app/` 안의 Python으로 `app/` 을 교체하려 들면 자기 발밑을 치우는 셈이다.
