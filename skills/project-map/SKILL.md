# project-map

현재 프로젝트를 **전수 스캔**해 "이 시스템이 어떻게 동작하는가"를 한 장의 **자립형 HTML 페이지**로 그린다.
Claude_Manager의 `/ecosystem` 페이지와 같은 결의 시각화지만, **대상 프로젝트 본인 폴더에** 만든다.

## 어디에 만드나 (중요)
- **결과물은 스캔 대상 프로젝트 자기 폴더**에 저장한다. 기본 경로: **`docs/project-map.html`**
  (`docs/`가 없으면 만든다). Claude_Manager 허브에 넣지 않는다. **이 경로·파일명은 규약**이다 —
  Project_Manager가 이 정확한 위치를 보고 찾으므로 바꾸지 말 것.
- 이유: 이 페이지는 **Project_Manager가 프로젝트별로 조회**한다. 그래서 각 프로젝트에 함께 커밋돼야 한다.
  - Project_Manager는 프로젝트 cwd 기준 `<cwd>/docs/project-map.html` 를 자동 감지해, 프로젝트 페이지에
    "🗺️ 구조 맵" 버튼과 대시보드 카드 배지를 띄우고 iframe 뷰어로 보여준다(Windows cwd `C:\…` 는
    `/mnt/c/…` 로 자동 변환해 읽음). 별도 등록 절차 없이 파일만 있으면 된다.
- 자립형(self-contained): 인라인 CSS/JS만, 외부 의존 0 → 브라우저로 바로 열리고 어디든 이식된다.
  (Project_Manager도 iframe 격리로 그대로 렌더하므로 자립형이 아니면 깨진다.)

## 언제 쓰나
- 사용자가 "이 프로젝트 구조/아키텍처 시각화", "동작 구조 페이지 만들어", `/project-map` 등을 요청할 때.

## 절차

### 1) 전수 스캔 (빠짐없이)
샘플링 금지 — 소스 전체를 훑는다.
```bash
# 구조 파악(노이즈 제외)
find . -type f -not -path '*/node_modules/*' -not -path '*/.git/*' -not -path '*/.next/*' \
  -not -path '*/dist/*' -not -path '*/build/*' | sort
# 스택/진입점 힌트
cat package.json 2>/dev/null; ls -a
```
프로젝트가 크면 **상위 디렉터리/모듈별로 서브에이전트(Task/Explore)를 팬아웃**해 각자 분류·요약을
받아 취합한다(대형이어도 누락 없이 커버).

### 2) 역할 분류 (모든 파일)
각 소스를 아래 계층 중 하나로 분류하고, 스택에 맞게 **엔드포인트를 실제로 추출**한다:
- **진입점(Entry)** — main/index/server bootstrap, CLI 엔트리, `package.json` scripts.
- **엔드포인트(Endpoint)** — HTTP 라우트/핸들러, API, CLI 명령, 이벤트 구독, 웹훅 등 외부 노출 표면.
- **엔진(Engine·핵심 로직)** — 도메인/비즈니스 로직, 서비스, 파서, 계산·상태 처리 등 "일하는" 모듈.
- **데이터·저장(Data)** — DB·모델·마이그레이션·파일 저장·캐시·상태.
- **외부 연동(External)** — 서드파티 API/서비스/SDK/MCP.
- (있으면) **백그라운드·스케줄(Jobs)**, **설정·빌드(Config/Build)**.

그리고 **노드 사이의 실제 연결(엣지)을 뽑는다** — 이게 플로우차트의 핵심이다.
- 큰 방향은 진입점 → 엔드포인트 → 엔진 → 데이터/외부지만, **막연한 계층 연결이 아니라
  "이 노드가 저 노드를 실제로 호출/import/라우팅하는가"**를 코드 근거로 잇는다.
- 한 노드가 **여러 곳으로 분기**할 수 있다(예: 한 엔진이 데이터 저장 + 외부 API 둘 다 호출).
- 근거 없는 연결은 만들지 않는다. 실제 코드에 있는 관계만 엣지로 남긴다.

또 **프로젝트에서 사용자가 할 수 있는 "기능"을 빠짐없이 나열**하고, 각 기능마다 그것을 쓸 때
거치는 **흐름 경로(노드 id 들)**를 정한다. (예: "통합 검색" = 검색 화면 → 검색 API → 검색 엔진 →
집계 → 파서 → jsonl.) 이게 FEATURES 가 된다 — 화살표가 많아도 기능을 클릭하면 그 경로만 강조된다.

### 3) 자연어로 이름 붙이기 (가독성 규칙)
- **메인 라벨 = 사람이 읽는 자연어.** 예: `authMiddleware` → **"사용자 인증 검사"**,
  `POST /orders` → **"주문 생성 API"**, `sync-wsl.sh` → **"환경 동기화"**.
- **식별자(파일 경로·함수/변수명·라우트 패턴)는 보조 정보**로 작은 모노스페이스 서브라인에 둔다.
- 각 노드에 **한 줄 목적 설명**(무엇을/왜)을 자연어로 붙인다.
- 요약·추상화하되 **실제 코드에 근거**한다(위조 금지).

### 4) HTML 생성 (같은 폴더 `TEMPLATE.html` 기반) — **흐름 자동 배치 플로우차트**
- `TEMPLATE.html`을 복사·채워 `docs/project-map.html`로 저장한다. **위치는 손으로 정하지 않는다** —
  노드와 EDGES만 채우면 JS가 **EDGES로 각 노드의 깊이(호출 순서)를 계산해 좌→우 레이어로 자동
  배치**하고, 연결된 노드 높이를 맞춰 교차를 줄이며, 방향이 보이는 좌→우 곡선+화살표로 잇는다.
  (모든 엣지가 오른쪽으로 흐르도록 보장되어 "흐름"이 실제로 보인다.) 채우는 법:
  - **헤더/스탯**: 프로젝트명 · 스택 · 스캔 시각 · 수치 타일.
  - **노드(요소)**: `#pm-graph` 안에 `<article class="pm-node" id="..." data-cat="...">` 를
    **순서 상관없이 flat 하게** 나열(카테고리별로 줄 세우지 말 것 — 배치는 JS가 한다).
    - `id` = 고유값(엣지에서 참조, 필수). `data-cat` = `entry|endpoint|engine|data|external`(색·범례용).
    - 내용 = `pm-cat`(작은 카테고리 라벨) + `pm-title`(자연어 이름) + `pm-sub`(식별자 경로/심볼) +
      `pm-desc`(한 줄 목적).
  - **연결(엣지)**: 하단 `<script>`의 **`EDGES` 배열**을 `[출발id, 도착id]` (또는 라벨을 붙이려면
    `[출발id, 도착id, "설명"]`) 로 채운다. 2)에서 뽑은 실제 관계만. **이게 배치의 근거**다 — 엣지가
    부실하면 흐름도 부실해진다. 없는 id 는 무시. 순환(cycle)은 피한다(호출 흐름은 DAG로 본다).
    - **선은 검정 단색**, 화살촉은 작게(가독성 위주 — 색 구분은 노드 상단 테두리 색이 담당).
    - 3번째 "설명"은 **항상 엣지 중앙에 작은 라벨**로 표시된다(호출 함수·관계 등, 1~2단어 권장).
      **라벨을 클릭하면 그 엣지만 강조**된다. 라벨은 노드 **아래** 레이어라 노드를 가리지 않는다
      (설명이 선을 일부 덮는 건 허용).
  - **기능 목록(`FEATURES`)**: `<script>`의 `FEATURES` 배열에 `{id, name, desc, nodes:[...]}` 로
    2)에서 뽑은 기능을 **전부** 채운다. `nodes` = 그 기능 흐름 경로의 노드 id 들. `desc` = 그 기능이
    하는 일 **한 줄 설명**(자연어). 상단 칩으로 렌더되고, 칩을 클릭하면 그 경로만 강조되며 **칩 줄
    아래 캡션 바에 `name — desc`** 가 뜬다. (기능이 흐름을 이해하는 진입점이므로 빠뜨리지 말 것.)
  - **상호작용은 자동**: 노드 클릭=이웃 강조, 칩 클릭=기능 흐름 강조, 엣지 라벨 클릭=그 연결만
    강조. 코드 손댈 것 없음.
  - **흐름 밖 독립 항목**(설정·빌드 등, 엣지 없음)은 그래프에 넣지 말고 `pm-aux`에 둔다.
  - **범례**와 하단 "재생성: `/project-map`" 안내는 그대로 둔다.
- **공간을 크게 쓴다 — 어거지로 한 화면에 욱여넣지 말 것.** 그래프는 zoom/pan 뷰포트 안에서
  화면보다 커도 되고, 로드 시 자동 맞춤된다. 노드가 많아도 우하단 `＋ / － / ⤢(맞춤)`·드래그 팬으로 본다.
- 반드시 **자립형**(인라인 CSS/JS만, 외부 링크·CDN·폰트 금지), **배경은 light 고정**
  (`color-scheme:light`), **반응형**. (Project_Manager가 iframe 으로 조회 — 뷰어 테마와 무관하게 밝게.)

### 5) 보고
저장 경로, 계층별 노드 수, 눈에 띄는 구조 특징 1–2개를 사용자에게 요약한다.
브라우저로 여는 법도 알려준다(WSL: `explorer.exe docs/project-map.html`, 또는 파일 직접 열기).

## 품질 체크 (저장 전 자문)
- **모든 소스 파일이 어딘가에 반영**됐는가(빠진 폴더·엔드포인트 없나)?
- 메인 라벨이 **자연어**인가(변수명 그대로 노출하지 않았나)? 식별자는 보조로 갔나?
- 노드 목적이 **실제 코드에 근거**하는가?
- **모든 노드에 고유 id 가 있고, EDGES 가 실제 관계로 채워졌는가**(선이 그려지나)? 고아 노드가
  너무 많지 않은가? 근거 없는 연결을 지어내지 않았나?
- 배경이 **light 고정**인가(다크 잔재 없나)?
- 외부 의존 없이 **파일 하나로 열리는가**(인라인 CSS/JS만)?

## 설계 메모
- 이 skill의 단일 원본은 `Claude_Manager/skills/project-map/`, 각 환경 `~/.claude/skills/`에 설치
  (WSL 심링크·Windows 복사 — `scripts/sync-*`).
- 산출물(`docs/project-map.html`)은 **대상 프로젝트에 커밋**한다(허브 아님). Project_Manager가 그걸 조회.
