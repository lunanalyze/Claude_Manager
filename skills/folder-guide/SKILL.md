# folder-guide

프로젝트를 **전수 스캔**해 "이 폴더에 뭐가 있고, 각 파일이 무슨 일을 하는가"를 **Artifact 한 장**으로 만든다.
처음 이 저장소를 여는 사람(또는 6개월 뒤의 나)이 **파일을 열어보지 않고도** 어디를 봐야 할지 알게 하는 것이 목적이다.

내용 구성은 둘로 고정된다:
1. **전체 구조 — mermaid 다이어그램** (폴더가 노드, 폴더 사이의 실제 관계가 엣지)
2. **폴더를 따라 내려가며 설명** (주석 붙은 트리 + 폴더별 파일 표)

## project-map과의 차이 (둘 다 있어도 겹치지 않는다)

| | project-map | **folder-guide** (이 skill) |
|---|---|---|
| 답하는 질문 | 이 시스템이 **어떻게 동작하나** | 이 폴더에 **뭐가 들어 있나** |
| 단위 | 진입점·엔드포인트·엔진·데이터 (역할 노드) | **폴더와 파일** (있는 그대로) |
| 대상 | 소스 코드 | 소스 + **문서·데이터·빌드·자산·찌꺼기까지 전부** |
| 결과물 | `docs/project-map.html` (프로젝트에 커밋) | **Artifact 페이지** (링크로 공유) |

project-map은 코드가 아닌 것(자료 폴더, 설치본, 로그, 백업 zip)을 다루지 않는다.
folder-guide는 **저장소에 실제로 있는 모든 것**을 다룬다 — 용량의 대부분이 코드가 아닌 프로젝트가 흔하고,
"이 400MB짜리 폴더는 뭔가"에 답하는 것이 이 문서의 값어치다.

## 어디에 만드나 — **Artifact**
- 결과물은 **Artifact로 발행**하고 사용자에게 **URL을 전달**한다. 로컬 md 파일로 끝내지 않는다.
- HTML을 **scratchpad 디렉터리**에 쓰고 그 경로로 `Artifact` 를 호출한다(프로젝트 폴더를 더럽히지 않는다).
- 같은 세션에서 고칠 때는 **같은 파일 경로로 다시 발행**하면 URL이 유지된다.
  이전 세션에서 만든 것을 갱신하려면 `action:"list"` 로 URL을 찾아 `url` 인자로 넘긴다(새 링크가 생기지 않게).
- 사용자가 저장소에도 두길 원하면 같은 HTML을 `docs/folder-guide.html` 로 복사해 커밋한다(요청이 있을 때만).

## 언제 쓰나
- "이 프로젝트 폴더 구조 설명해줘", "어떤 파일이 뭐 하는지 정리", "폴더 사전", `/folder-guide`.
- 처음 인수인계받은 저장소를 파악할 때. 정리(삭제) 전에 무엇이 남아 있는지 훑을 때.

## 절차

### 1) 지형 파악 — 세 가지를 한 번에 잰다
구조·**용량**·**줄 수**를 함께 봐야 무엇이 중요한지가 드러난다. 이름만으로는 알 수 없다.

```bash
# 구조 (노이즈 제외)
find . -maxdepth 3 -not -path './.git/*' -not -path '*/node_modules/*' -not -path '*/.venv/*' \
  -not -path '*/.next/*' -not -path '*/__pycache__/*' | sort

# 폴더 용량 — "이 폴더 왜 이렇게 큰가"가 여기서 나온다
du -sh */ 2>/dev/null | sort -rh

# 소스 줄 수 — 큰 파일이 대개 그 프로젝트의 심장이다
find . -name '*.py' -o -name '*.java' -o -name '*.ts' -o -name '*.tsx' | xargs wc -l | sort -n

# 무엇을 커밋하지 않는지 = 무엇이 민감한지
cat .gitignore; git status --short; git log --date=short --format='%ad %h %s' | head -30
```

> ⚠️ **`du`는 큰 저장소에서 멈춘다.** `node_modules`·`build`·`.git`이 큰 프로젝트에서 `du -sh */`가
> 2분을 넘겨 백그라운드로 밀린 실측 사례가 있다(6GB 저장소). 최상위만 재고, 오래 걸리면
> 무거운 폴더를 빼고 다시 잰다. Windows 경로는 **공백·한글이 흔하므로 항상 인용**한다.

프로젝트가 크면 **최상위 폴더별로 서브에이전트(Explore/Task)를 팬아웃**해 각자 요약을 받아 취합한다.

### 2) 파일이 하는 일 알아내기 — **파일 자신에게 묻는다**
이 skill의 품질은 여기서 갈린다. 파일명으로 추측하지 말고 **파일이 스스로 밝힌 목적**을 가져온다.

우선순위:
1. **모듈 독스트링 / 클래스 주석 맨 위** — 잘 쓰인 프로젝트는 여기에 "왜 이게 존재하는가"가 있다.
   실제로 가장 값어치 있는 설명은 전부 여기서 나왔다(예: 어떤 파일의 독스트링이 "차트를 그림으로
   굽는 이유 = 망연계 무해화가 임베디드 워크시트를 걷어내며 문서를 못 열게 만들었다"는 실측
   사고 경위를 담고 있었다 — 코드만 봐서는 알 수 없는 정보다).
   ```bash
   # 파이썬·자바 첫 주석 블록만 싸게 훑기
   head -30 src/*.py | grep -vE '^import|^from|^$'
   grep -B2 -A12 '^/\*\*' service/**/*.java | head -100
   ```
2. **README·설계 문서** — 단 코드와 어긋나면 **코드가 정답**이다(§6).
3. **호출부** — 아무 설명이 없으면 누가 이 파일을 부르는지로 역할을 좁힌다.
4. 그래도 모르면 **"확인 불가"로 적는다.** 지어내지 않는다.

> 📌 **위조 금지(작업 규칙 2).** 열어보지 않은 파일에 그럴듯한 설명을 붙이지 않는다.
> 이 문서는 "파일을 안 열어도 되게" 하려는 것이라, 틀린 한 줄이 특히 비싸다.

### 3) 전체 구조 — mermaid 다이어그램
**폴더가 노드**, **폴더 사이의 실제 관계가 엣지**다. 트리를 mermaid로 다시 그리지 않는다
(그건 4)의 트리가 이미 한다 — 중복이다). 여기서 보여줄 것은 **누가 누구를 먹여주는가**다.

```
flowchart LR
  subgraph apps["apps/ — 앱 셋"]
    web["apps/web/<br/>Next 화면"]
    api["apps/api/<br/>Spring 서버"]
    docx["apps/docx/<br/>파이썬 사이드카"]
  end
  data[("data/<br/>SQLite + run 폴더")]
  tools["tools/installer/<br/>설치본 빌드"]

  web -->|"정적 export"| api
  api -->|"subprocess"| docx
  api -->|"메타·산출물"| data
  tools -->|"셋을 묶어 패키징"| apps
```

규칙:
- **노드는 폴더**(최상위 + 필요한 만큼 한 겹). 파일 단위로 내려가지 않는다 — 20개 안쪽으로 유지.
- **엣지는 코드 근거가 있는 관계만.** "같은 계층이라서" 잇지 않는다. 라벨에 관계를 적는다
  (`서빙`, `subprocess 호출`, `읽는다`, `빌드해 담는다`).
- **역할이 다른 묶음은 `subgraph`**로 감싼다(앱 / 데이터 / 빌드 / 자산).
- 코드가 아닌 폴더(자료·산출물·백업)도 **관계가 있으면 노드로** 넣는다. 없으면 넣지 말고 표로만 다룬다.

**mermaid 함정 (렌더 실패의 실제 원인들)**
- 라벨에 `/` `.` `(` `)` `-` 공백이 들어가면 **큰따옴표로 감싼다**: `web["apps/web/"]`. 안 감싸면 파싱이 깨진다.
- **역슬래시 금지.** Windows 경로라도 mermaid 라벨에는 `apps/web/`처럼 `/`로 쓴다(`\`는 이스케이프로 먹힌다).
  본문 산문에서는 `apps\web\`으로 써도 된다.
- **예약어를 노드 id로 쓰지 않는다** — `end`, `graph`, `subgraph`, `class`, `style`, `click`, `default`.
  특히 `end`는 subgraph를 통째로 망가뜨린다.
- 줄바꿈은 `<br/>`. 한글은 그대로 써도 되지만 괄호가 들어가면 따옴표로 감싼다.
- 방향은 계층이면 `TB`, 흐름이면 `LR`. 대개 `LR`이 읽기 좋다.

### 4) 폴더를 따라 내려가며 — 주석 붙은 트리
최상위 트리 한 장에 **폴더마다 한 줄 역할**을 붙인다. 규모(줄 수·용량)를 같이 적으면 무게가 보인다.

```
프로젝트루트/
├─ src/          36 파일 13,746줄   기능 엔진 전부
├─ web/          app.py 2,843줄     서버 + 정적 화면
├─ prompts/      17개               LLM 지시문 (schema와 1:1 짝)
├─ 자료/         424MB              실 안건 원본 — 검증 입력
└─ output/       119MB              생성 결과 20건
```

### 5) 폴더별 파일 표
트리에서 짚은 폴더를 **하나씩 내려가며** 표로 푼다. 열은 `파일 | 줄수(또는 크기) | 설명`.

- 파일이 많으면 **역할 그룹으로 묶어** 소제목을 준다(예: `f1 파이프라인` / `수집` / `검증` / `공통`).
- **줄 수 내림차순**이 대개 좋은 순서다 — 큰 파일이 그 폴더의 중심이다.
- 설명은 **한두 문장**. 그 파일만의 사실을 하나 넣는다(왜 존재하는지, 무엇에 묶여 있는지, 함정).
  일반론("유틸리티 모음")만 적을 거면 차라리 짧게 쓴다.
- 잔챙이 파일은 **한 줄에 묶어** 처리한다(`favicon 4종`, `Gradle 래퍼 일습`).

### 6) 흔적·불일치 수집 — **찾되 고치지 않는다**
스캔하다 보면 반드시 나온다. 모아서 **보고만** 한다(작업 규칙 1 — 시킨 것만).

찾을 것:
- **0바이트 파일**, 백업 zip, `_old`·`_bak`·버전 접미사 폴더.
- **죽은 참조** — 메모·설정이 가리키는 경로/포트가 지금 없는 것.
- **낡은 빌드 산출물** — 버전이 현재 버전과 다른 설치본·팩.
- **git 미추적인데 gitignore에도 없는 폴더** (`git status --short`에 `??`로 뜬다).
- **문서 ↔ 코드 불일치** — README의 포트와 실제 스크립트의 포트가 다른 식.
  → 별도 절로 모으고, **"코드가 정답"**을 전제로 양쪽을 나란히 적는다.
- **포트**가 나오면 포트 점유 표준(`Claude_Manager/docs/standards/ports.md` — CLAUDE.md가 import한다)의
  배정과 대조해 어긋나면 적는다. 표와 코드가 다르면 **표가 기준**이고, 고치지 않고 적기만 한다.

### 7) Artifact 작성·발행
**HTML을 쓰기 전에 `artifact-design` 스킬을 먼저 로드**한다(디자인 수준 보정). 그다음:

1. scratchpad에 `.html` 로 저작한다. `<!doctype>`·`<html>`·`<head>`·`<body>` 태그는 쓰지 않는다
   (발행 시 감싸진다). 파일 맨 위에 `<title>` 과 `<style>` 을 둔다.
2. **`<title>` = `<프로젝트명> 폴더 사전`** 같은 짧은 고유명. 설명을 붙이지 않는다.
   `Artifact` 호출 시 `description` 에 한 문장 요약, `favicon` 에 이모지(첫 발행에만).
3. **mermaid는 라이브러리를 로드하지 않는다.** Artifact가 네이티브로 렌더한다 —
   HTML에서는 **`<pre class="mermaid">…</pre>`** 블록에 그대로 넣으면 된다.
4. 트리는 `<pre>` 에 넣고 **`overflow-x:auto`** 를 준다. 표도 각자 스크롤 컨테이너에 담는다
   (페이지 본문이 가로로 밀리면 안 된다).
5. 발행 후 URL을 사용자에게 전달한다.

### 8) 보고
저장 URL, 폴더 수·파일 수, **눈에 띈 구조 특징 1~2개**, **§6에서 모은 흔적·불일치 목록**을 요약한다.

## 페이지 절 순서 (고정)

1. **머리말** — 무엇에 대한 문서인가, 언제 실측했는가, 대상 경로.
2. **한눈에** — 스택·규모(줄 수)·총 용량. 표 하나.
3. **전체 구조** — mermaid (§3).
4. **루트 트리** — 주석 붙은 트리 (§4).
5. **폴더별 상세** — 폴더 하나당 소제목 + 파일 표 (§5). 페이지의 몸통.
6. **흔적과 불일치** — (§6).
7. **확인 방법** — 어떤 명령으로 쟀는지. 재현 가능하게.

## 무엇을 적지 않나
- **파일 내용 요약본**. 이 문서는 색인이지 사본이 아니다.
- 열어보지 않은 파일의 추측성 설명.
- 고치라는 지시. 흔적을 찾아도 **적기만** 한다.
- `node_modules`·`.git`·`__pycache__` 내부. 존재와 용량만 한 줄로.

## 품질 체크 (발행 전 자문)
- **모든 최상위 폴더가 문서에 등장**하는가? 빠뜨린 폴더·루트 파일 없나?
- 각 파일 설명이 **실제 파일 근거**인가? 독스트링을 봤나, 이름만 보고 썼나?
- **확인 못 한 것을 "확인 불가"로 명시**했나? 얼버무리지 않았나?
- mermaid가 **실제로 렌더되는가**? 따옴표·예약어·역슬래시를 확인했나?
- 줄 수·용량이 **실측값**인가? (`wc -l`·`du` 출력에서 왔는가)
- 흔적·불일치를 **고치지 않고 보고만** 했나?
- 이 페이지만 읽고 **"어디를 열어야 할지" 판단**이 서는가?

## 설계 메모
- 단일 원본 `Claude_Manager/skills/folder-guide/`, 각 환경 `~/.claude/skills/`에 설치
  (WSL 심링크 `scripts/sync-wsl.sh` · Windows 복사 `scripts/sync-windows.ps1`).
- **TEMPLATE 파일을 두지 않는다.** 결과물이 Artifact라 룩앤필은 `artifact-design` 스킬이 그때그때
  보정하는 것이 맞고, 고정 HTML 골격을 두면 매번 같은 페이지가 나온다. 이 skill이 고정하는 것은
  **내용 구성(절 순서)**뿐이다.
- 산출물이 프로젝트에 커밋되지 않으므로 **구조가 바뀌면 다시 돌려 같은 URL로 재발행**한다
  (`action:"list"` 로 URL을 찾아 `url` 인자로 넘긴다).
- `project-map`과 짝으로 쓰면 좋다 — folder-guide로 **무엇이 있는지**, project-map으로
  **어떻게 흐르는지**.
